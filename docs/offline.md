# 離線與同步（L1、L2）

所有的讀寫都在這台裝置的 IndexedDB（資料庫名稱 `mdrawer`）完成，所以沒有網路時照樣可以新增、修改、移動、刪除。修改會先放進「待同步佇列」，連線時在背景推送到 Supabase，再把其他裝置的修改拉回來（spec 第 6 節）。

| 檔案 | 負責 |
| --- | --- |
| `src/lib/localDb.ts` | IndexedDB 的結構：`nodes`（每個項目在這台的樣子）、`pending`（待同步佇列）、`meta`（擁有者、拉取進度） |
| `src/lib/repo.local.ts` | 畫面用的 repo：讀寫本機，修改同時記進佇列；名稱規則、同層不可同名、不能移進自己底下，先在本機檢查 |
| `src/lib/sync.ts` | 推送、拉取、衝突處理 |
| `src/lib/cloud.ts` | 同步用的 Supabase 請求（新增、依版本更新、分頁拉取） |
| `src/lib/mirror.ts` | 什麼時候同步、資料屬於哪個帳號、登出時怎麼處理 |

UI 一樣只呼叫 `repo.ts`，不知道資料是不是已經同步。

## 運作方式

| 情況 | 讀寫文字資料 | 圖片 | 畫面 |
| --- | --- | --- | --- |
| 連線且已登入 | 本機，背景同步 | 可以插入、顯示 | 側欄顯示「已同步：時間」或「N 項修改等待同步」 |
| 斷線 | 本機，等恢復連線 | 不能插入；沒載入過的顯示「離線時無法載入圖片」 | 上方提示「離線中：修改會先存在這台裝置…」 |
| 離線期間登入權杖過期（見下方） | 本機，等登入恢復 | 同上 | 恢復連線後顯示「正在確認登入狀態…」 |
| 第一次在這台裝置登入 | 先整批下載 | — | 「正在下載你的筆記…」 |

### 什麼時候同步

App 開啟、恢復連線、登入恢復時，每 30 秒一次，以及在這台裝置修改後 2 秒（讓另一台裝置早點看到）。同一個瀏覽器開了多個分頁時，用瀏覽器的 Web Locks 讓它們輪流同步。

### 推送

每個項目在佇列裡只有一筆：多次修改合併，記下改了哪些欄位，以及修改前的雲端版本（`version` 與當時的名稱、位置、內容）。推送順序：

1. **刪除**，子項目先、資料夾後。反過來的話，其他裝置剛好在中間同步，會看到「資料夾已刪除、裡面的還在」。刪除排在最前面，也讓「刪掉舊的、再建同名的」不會撞名。
2. **新增**，父先子後（spec 第 6 節），否則子項目會因為上層還不在雲端而失敗。用 `upsert` + `ignoreDuplicates`，重送也安全。
3. **修改**（內容、改名、移動），照修改的順序。用 `update … where id = ? and version = 修改前的版本`，沒有回傳資料列就是雲端被別台改過，進入衝突處理。

推送期間如果又改了同一個項目，新的修改不會被清掉，下一輪再推。斷線會中止這一輪，佇列保留。

### 拉取

推送完之後，讀取「上次看到的最後時間往前 10 秒」之後的所有列（包含已刪除的），用 `id` + `version` 去掉重複，寫回本機。往前多抓 10 秒，是因為資料庫的 `updated_at` 是交易開始的時間，晚一點 commit 的修改時間可能比上次看到的還早（ai-log 11/23）。時間一律用雲端回傳的值。

這台還有沒推送的修改時，拉到的版本不覆蓋它，下一次推送時再處理衝突。

### 衝突處理（spec 第 6 節）

| 情況 | 結果 |
| --- | --- |
| 沒有衝突（`version` 吻合） | 直接成功 |
| 兩邊都改了同一篇的內容 | 雲端的版本保留在原筆記；這台的版本另存為「名稱（衝突副本 2026-11-25 14:30）」，放在同一個資料夾。側欄會提示，由你自己合併 |
| 一邊改名或移動、一邊改內容 | 兩個修改都保留 |
| 兩邊都改名或都移動 | 較晚推送的為準 |
| 一邊刪除、一邊修改 | 刪除不會蓋掉修改：項目保留（修改的那台會把它還原），刪除的那台下次同步會拿回來 |
| 同名（另一台剛好建了同名的） | 自動加「 (2)」，這台也跟著改名 |
| 推送成功但沒收到回應 | 重送時發現雲端已經是這台的樣子，視為成功，不建立衝突副本 |
| 上層資料夾已被另一台刪除 | 放到根目錄 |
| 兩台交叉移動資料夾（會形成循環） | 後推送的那個移動改成放在根目錄 |

**編輯時剛好同步到另一台的修改**：編輯器記得這次是根據哪個內容改的。儲存時如果發現這篇已經被同步改過，不會蓋掉，這次的內容直接另存為衝突副本，編輯器換成同步來的版本，並顯示說明。

### 帳號與登出

- 本機資料記下屬於哪個帳號。換成別的帳號登入時，先清除前一個帳號的資料。
- **自己登出**（右上角選單的「登出」）：還有未同步的修改時，能連線就先同步一次；還有剩下的，就跳出「還有修改沒有同步」，確認後才清除（spec 第 6 節登出保護）。
- **被強制登出**（在其他分頁登出、在別處改密碼、全部登出等）：
  - 沒有未同步的修改：清除本機資料。
  - 有未同步的修改：先保留。登入畫面會提示「這台裝置上有 N 項修改還沒同步」，用同一個帳號登入後自動同步。
  - 改用別的帳號登入：先問「刪除這些修改並繼續」或「改用原帳號登入」。

### 離線期間登入權杖過期

Supabase 的登入權杖約 1 小時過期，離線時換不到新的，supabase-js 會把登入狀態回報成「未登入」。如果照這個狀態顯示登入表單，隔天沒網路時打開 App 就看不到筆記。

所以：沒有有效登入、但這台裝置有本機資料（而且不是被強制登出留下的）時，就用本機資料的帳號開啟，照樣可以讀寫。恢復連線時 App 會立刻請 supabase-js 重試換權杖，成功後自動同步。supabase-js 換權杖失敗後會冷卻 60 秒，所以最久大約 1 分半；重新整理頁面可以馬上重試。

## 驗證

用部署網址（或 `npm run build && npm run preview`）測。開發模式沒有 service worker，斷線後重新整理會打不開。

**兩台裝置**：用兩個不同的瀏覽器（例如 Chrome 和 Safari），或電腦加手機。Chrome 的無痕視窗也有自己的 IndexedDB，可以當第二台（關掉無痕視窗後資料就沒了）。

| # | 操作 | 預期結果 |
| --- | --- | --- |
| 1 | 登入，等幾秒 | 側欄出現「已同步：時間」 |
| 2 | F12 → Application → IndexedDB → `mdrawer` | `nodes` 是你的資料夾與筆記；`pending` 是空的；`meta` 有 `owner`、`cursor` |
| 3 | F12 → Network 改成 **Offline**，新增資料夾與筆記、改內容、改名、移動、刪除 | 都可以做；側欄「N 項修改等待同步」；`pending` 有對應的項目 |
| 4 | 維持 Offline，重新整理頁面 | 剛才的修改都還在，可以繼續編輯 |
| 5 | 改回 No throttling | 幾秒內變成「已同步」，`pending` 清空 |
| 6 | 在第二台打開（或等 30 秒、重新整理） | 看得到第 3 步的所有修改 |
| 7 | 兩台都斷線，改同一篇筆記的內容，A 先恢復連線、B 再恢復 | B 的側欄提示衝突；原筆記是 A 的版本，同一個資料夾多了「（衝突副本 …）」是 B 的版本；A 同步後也看得到副本 |
| 8 | A 改名、B 改內容（同一篇），依序恢復連線 | 名稱與內容兩個修改都在 |
| 9 | A 刪除、B 改內容（同一篇），依序恢復連線 | 筆記保留，內容是 B 改的 |
| 10 | 斷線時改一個字，從右上角選單按「登出」 | 跳出「還有修改沒有同步」；按取消不會登出 |
| 11 | 連線、沒有待同步的修改時從右上角選單按「登出」，再看第 2 項 | `nodes`、`pending`、`meta` 都是空的（可能要在 IndexedDB 上按右鍵 Refresh） |
| 12 | 終端機執行 `npm run test:sync` | 全部 ✓。這是在真正的 Supabase 上檢查同步用的請求，見下方 |

**`npm run test:sync`**：用 `.env.test.local` 的 A、B 測試帳號（同 `npm run test:rls`），直接執行 App 的 `src/lib/cloud.ts`，檢查以下幾項：

- 重送新增不會覆蓋
- 版本不符時不更新
- 撞名與外鍵錯誤的判斷
- 標記刪除與還原
- 分頁拉取接續讀取且包含已刪除的列
- B 帳號碰不到 A 的資料
- 刪除資料夾裡的圖片後清掉 Storage 的檔案：還有副本或舊筆記（`![](img:…)`）用到時保留、B 帳號刪不到 A 的檔案、沒有地方用到時才刪

測試資料會放在「同步測試 <時間>」資料夾，結束時實際刪除；圖片的檢查會上傳一個測試用的小檔案，結束時也會刪掉。

**模擬「離線期間權杖過期」**（可選）：登入後在 F12 → Application → Local Storage → `sb-…-auth-token`，把 `"expires_at":` 後面的數字改成比現在小（例如 `1700000000`），再照第 4 步斷線重新整理：仍能開啟並編輯。恢復連線後幾秒到 1 分半內自動同步。

自動化測試：`npm test` 裡的 `sync.test.ts` 模擬兩台裝置與雲端，涵蓋上面的衝突表與邊界情況；`mirror.test.ts` 涵蓋帳號、登出與從 L1 升級。

## 已知限制

- **不是即時同步**：最慢約 30 秒才會看到另一台的修改（App 開啟、恢復連線、修改後 2 秒也會同步）。
- **衝突不會自動合併**：同一篇內容兩邊都改時，要自己對照衝突副本合併。名稱與位置以較晚推送的為準。
- **圖片**離線時不能插入、不能上傳到資料夾，沒載入過的也無法顯示（圖片檔只存在雲端）。資料夾裡的圖片離線時照樣可以改名、移動、複製、刪除；刪除的圖片，同步後沒有其他地方用到時才刪掉雲端的檔案。
- **一台刪除圖片、另一台離線時改了同一張圖片的名稱或位置**：依「修改優先」會還原這張圖片，但先同步的那台可能已經刪掉了檔案，還原後顯示找不到圖片。
- **同一個瀏覽器的另一個分頁**，要等它自己同步（最多 30 秒）或重新整理，畫面才會更新。
- **被強制登出、留下未同步的修改**時，重新登入前，未加密的資料會留在裝置上。
- **刪除很大的資料夾**時，每個項目各推送一次，項目多時要一點時間。
- **拉取往前多抓 10 秒**：commit 比交易開始晚超過 10 秒的修改可能漏掉。App 的每個請求都很短，實務上不會發生。
- 瀏覽器在儲存空間不足時可能清除 IndexedDB，還沒同步的修改會跟著消失。離線很久的話，恢復連線後讓它同步完成，並定期匯出 ZIP。
